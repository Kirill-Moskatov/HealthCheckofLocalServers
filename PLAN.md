# Pulse — план разработки

Дашборд healthcheck для домашних сервисов. Рабочее название: **Pulse** («пульс» домашних сервисов).

> Статус документа: черновик плана, ждёт согласования.
> Главный файл для транзишна контекста между чатами — [`AGENTS.md`](./AGENTS.md). Новый чат всегда начинает с него.

---

## 1. Цель

Личный дашборд на внешнем сервере, который раз в 20 минут проверяет доступность домашних сервисов по их внешним адресам (KeenDNS), фиксирует простои, показывает аптайм за 10 недель и присылает уведомления в MAX (на этапе MVP — мок бота).

## 2. Требования MVP

| # | Требование | Источник |
|---|-----------|----------|
| 1 | MVP: два сервиса, всё на одной странице | контекст |
| 2 | Сервисы: **Home Assistant** и **Immich** (ФотоХранилище), оба в Docker дома | контекст |
| 3 | Проверка: HTTP GET, ожидаем **200** (для HA — нюанс, см. §5) | контекст |
| 4 | Адреса сервисов — внешние, через KeenDNS. Проверки идут напрямую с внешнего сервера | контекст |
| 5 | Если сервис не отвечает — фиксируем момент начала простоя, показываем «лежит уже N» | контекст |
| 6 | Интервал проверок: **раз в 20 минут** | контекст |
| 7 | История: **3 месяца**, динамика за **10 недель**: аптайм, простой, % доступности | контекст |
| 8 | Уведомления через бота **MAX**: падение, восстановление, недельный дайджест. Пока — **мок** | контекст |
| 9 | Авторизация: IAM-сервис с **Yandex, VK и логином/паролем** | контекст |
| 10 | Деплой на внешний сервер **1 vCPU / 1 ГБ RAM** (рядом уже крутится Amnezia VPN) | контекст |

## 3. Архитектура

Один Python-процесс, одна SQLite-база, один контейнер. Минимум движущихся частей.

```
┌─────────────────────────── внешний сервер (1 vCPU / 1 GB) ───────────────────────────┐
│                                                                                       │
│  Docker Compose                                                                       │
│  ┌────────────────────────────────┐     ┌───────────────────────┐                     │
│  │ pulse (FastAPI + Uvicorn)      │     │ casdoor (IAM)         │                     │
│  │  · APScheduler (каждые 20 мин) │     │  · Yandex / VK OAuth  │                     │
│  │  · httpx-проверки сервисов     │     │  · логин/пароль       │                     │
│  │  · логика инцидентов           │     │  · SQLite внутри      │                     │
│  │  · Notifier (MAX-мок → MAX)    │     └───────────────────────┘                     │
│  │  · SQLite (pulse.db)           │                                                   │
│  │  · дашборд (статика, M3-стиль) │                                                   │
│  └──────────────┬─────────────────┘                                                   │
└─────────────────┼─────────────────────────────────────────────────────────────────────┘
                  │ HTTPS GET раз в 20 мин
                  ▼
        ┌──────────────────────┐          ┌──────────────────────┐
        │ Home Assistant (дом) │          │ Immich (дом)         │
        │ адрес.keenetic…      │          │ адрес.keenetic…      │
        │ Docker               │          │ Docker               │
        └──────────────────────┘          └──────────────────────┘
```

### Данные

- `services` — id, имя, url, expected_status, интервал (на будущее).
- `checks` — каждая проверка: service_id, время, ok, http_status, latency_ms. Храним 3 месяца, чистим cron-задачей.
- `incidents` — service_id, started_at, ended_at (null = ещё лежит), причина (http_status/timeout).
- `notifications` — лог отправленных (мок) уведомлений: тип (down/up/digest), текст, время.

### Расчёты

- **Текущий простой** = now − incidents.started_at (если инцидент открыт).
- **Аптайм за период** = (период − Σ длительностей инцидентов в периоде) / период × 100%.
- **Недельный дайджест**: % доступности за 7 дней по каждому сервису + список инцидентов.

## 4. Стек и почему он

| Что | Чем | Почему |
|-----|-----|--------|
| Язык | **Python 3.12** | выбор владельца, простота сопровождения |
| Веб | **FastAPI + Uvicorn** | асинхронный из коробки, авто-документация `/docs` — удобно дебажить |
| БД | **SQLite** | личное использование, нагрузки нет, бэкап = скопировать файл |
| ORM | **SQLAlchemy** | привычно, схема создаётся при старте (`create_all`), без миграций на MVP |
| Планировщик | **APScheduler** | интервальные проверки + cron-дайджест + ночная чистка истории |
| HTTP-клиент | **httpx** | async, таймауты из коробки |
| Конфиг | **pydantic-settings + `.env`** | все секреты и URL вне кода |
| Фронт | **один index.html + app.js + tokens.css (Material 3)** | нет node-сборки на сервере, минимум технологий для новичка |
| IAM | **Casdoor** (Docker, встроенный SQLite) | Yandex + VK + пароль из коробки, один лёгкий Go-контейнер |
| Упаковка | **Docker Compose** | всё в двух контейнерах, `docker compose up -d` |

**Вектор масштабирования** (не делаем сейчас, но ничего не блокируем): фронт → Vite + React + MUI; SQLite → PostgreSQL; проверки → отдельные воркеры, если сервисов станет 50+.

## 5. Ключевые решения и нюансы

1. **Home Assistant отдаёт 401 на `/api/` без токена** — это не сбой. Проверяем HA по `GET /manifest.json` (статика логин-страницы, 200 без авторизации). Для надёжности у каждого сервиса в конфиге свой `expected_status` (по умолчанию 200).
2. **Immich**: `GET /api/server/ping` → 200 `{"res":"pong"}` без авторизации.
3. **Порог сбоя = 1 неудачная проверка** (интервал 20 минут, сервисы личные — реагируем сразу). Настраиваемо на будущее.
4. **Точность инцидентов ограничена интервалом** (±20 мин) — осознанное упрощение MVP.
5. **Amnezia VPN не участвует** в проверках: сервисы доступны из интернета через KeenDNS. Amnezia — личный VPN владельца.
6. **MAX-бот — мок**: интерфейс `Notifier` + `MAXMockNotifier` (пишет в таблицу `notifications`, видно на дашборде). Реальный бот — отдельная задача после получения токена.
7. **Авторизация до публичного открытия**: этапы 4 (IAM) и 5 (деплой) не менять местами.

## 6. Этапы разработки

Каждый этап = **отдельный чат**. В конце этапа обязательно обновляется `AGENTS.md` (что сделано, что дальше). Новый чат читает `AGENTS.md` → `PLAN.md` → работает.

### Этап 0 — Скелет проекта
- Структура репозитория (см. §8), `config.py` (pydantic-settings, `.env.example`).
- Схема БД (4 таблицы), `create_all` при старте.
- FastAPI-приложение, `GET /health` самого Pulse.
- Dockerfile + dev-компоуз.
- **Готово, когда**: `docker compose up` поднимает приложение, `/health` → 200, файл БД создаётся.

### Этап 1 — Движок проверок
- APScheduler: проверки каждые 20 минут; хуки под дайджест и чистку истории (сами задачи — заглушки).
- `checker.py`: httpx GET, таймаут 10 с, сравнение с `expected_status`, запись в `checks`.
- Логика инцидентов: первая неудача открывает инцидент, первый успех закрывает.
- API: `GET /api/services` (статус + текущий простой), `GET /api/services/{id}/checks`, `GET /api/stats?weeks=10`, `POST /api/services/{id}/check` (ручной прогон).
- **Готово, когда**: проверки идут по расписанию и вручную, инциденты открываются/закрываются, API отдаёт статусы и аптайм за 10 недель.

### Этап 2 — Дашборд (Material 3)
- Одна страница: шапка со сводкой (X из Y в строю), карточки сервисов (статус, адрес, latency, «лежит с …», аптайм за 10 недель), лента инцидентов, полоски доступности по неделям, лог уведомлений (мок).
- M3: токены цветов/типографики, elevation карточек, статусные цвета, автообновление раз в 60 с, skeleton-состояния при загрузке.
- **Готово, когда**: страница показывает реальные данные из API и обновляется без перезагрузки.

### Этап 3 — Уведомления (мок MAX)
- `notifier.py`: интерфейс + `MAXMockNotifier`.
- События: `service_down`, `service_up`, `weekly_digest` (cron, утро понедельника).
- Запись в `notifications`, отображение на дашборде.
- **Готово, когда**: падение/восстановление и дайджест появляются в логе уведомлений.

### Этап 4 — Авторизация (Casdoor)
- Casdoor в компоузе (свой SQLite), приложение — OIDC-клиент.
- Провайдеры: Yandex, VK (нужны ключи приложений — инструкция в README), логин/пароль.
- Сессии, middleware защиты дашборда и `/api`.
- **Готово, когда**: без входа данные недоступны; вход паролем работает локально, Yandex/VK — при заполненных ключах.

### Этап 5 — Деплой (см. §7)
- **Готово, когда**: Pulse работает на внешнем сервере по HTTPS за авторизацией, проверки идут к KeenDNS-адресам, уведомления мокаются, неделя работы без вмешательства.

## 7. План деплоя (внешний сервер, 1 vCPU / 1 ГБ)

**Бюджет памяти** (ориентир): Amnezia ~250 МБ · Casdoor ~200 МБ · Pulse ~150 МБ · ОС ~200 МБ → впритык, поэтому:
- swap-файл 1–2 ГБ;
- `mem_limit` на контейнеры в compose;
- обе БД — SQLite (никаких отдельных контейнеров БД).

**Сеть и домен** — два варианта на выбор при деплое:
1. **Cloudflare Tunnel** (рекомендуется): бесплатный HTTPS, наружу не открываем ни одного порта, домен может быть бесплатный (или свой).
2. Свой домен + Caddy (авто-TLS), порты 80/443 наружу.

**Чек-лист деплоя**:
1. Docker + Compose на сервере (если нет), swap.
2. Домен/tunnel: поддомен `pulse.…` → Casdoor `auth.…` (или один домен с путями `/auth`).
3. `docker compose up -d` (pulse + casdoor).
4. В Casdoor: приложение Pulse, провайдеры Yandex/VK (client_id/secret из кабинетов разработчика), пользователь с паролем.
5. В `.env` Pulse: OIDC-настройки, URL сервисов KeenDNS.
6. Бэкап: cron раз в сутки копирует `pulse.db` + данные Casdoor (в облако или на домашний сервер).
7. Контрольная неделя: инциденты фиксируются, дайджест приходит, память не течёт (`docker stats`).

**Риски**: KeenDNS-адреса должны быть доступны именно с этого сервера (проверим curl'ом на этапе 1); при нехватке памяти — первый кандидат на урезание кэшей, второй — перенос Casdoor на домашний сервер.
